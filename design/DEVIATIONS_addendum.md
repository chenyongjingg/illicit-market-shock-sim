**Structure.** A run-time note and a definition may carry the same ID; they are different kinds
of object and live in different places. The stages append run-time notes above (blind `append`,
one per triggered condition -- D-34 is written once per grounding leg, so up to three times).
This section holds exactly **one definition per ID**, as a top-level entry, so that a definition
can never be rendered under the wrong parent: an indented paragraph belongs to whatever top-level
item precedes it in the file, not to the ID written in its text.

Every entry begins with a **kind marker** taken from a closed set, right after its timestamp:
`DEFINITION:` (what the implementation does, and what it may be called), `LIMITATION:` (a declared
defect that is not repaired in this run), `READING RULE:` (a rule for reading an existing number).
A marker may be followed by a parenthetical before its colon -- `DEFINITION (LIMITATION, declared not
repaired in this run):` -- so the pattern matches the word, not the colon. The whole set is therefore
retrievable, and countable, with one pattern **inside this section**:

```
sed -n '/^### Post-run definitions/,$p' DEVIATIONS.md   | grep -cE '^- \*\*(D|DP)-[0-9a-z]+\*\* \[[^]]+\] (DEFINITION|LIMITATION|READING RULE)'
```

**Both counts must be equal**: the number of top-level entries, `grep -cE '^- \*\*(D|DP)-'`, and the
number of kind-marked entries above them. Anchoring on the leading `- **D-n**` is what keeps a marker
quoted in prose (like the ones in this paragraph) from being counted as an entry.
